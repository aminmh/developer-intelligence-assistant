You are a coding agent implementing a domain-concept recognition layer in an existing RAG application.

Implement the feature using SQLite for canonical storage and Qdrant for semantic search. Reuse the existing application architecture, language, providers, and conventions.

## Goal

Recognize domain entities referenced in user prompts and resolve them to canonical entities extracted from project source code and documentation.

Examples:

- "the payment service" → PaymentService
- "the endpoint that creates an order" → POST /api/orders
- "what happens after an order is created?" → OrderCreated
- "which listener handles failed payments?" → relevant listener candidates
- "where is Mollie used?" → Mollie integration and verified dependencies

Extract technical entities and business concepts, not every grammatical noun.

Recognition must improve retrieval without treating uncertain matches or inferred relationships as established facts.

## 2. Storage architecture

Use:

- SQLite as the canonical source of truth for concepts, aliases, sources, relationships, and indexing state.
- Qdrant as a derived semantic index.
- Existing Neo4j infrastructure only if it is already used and relevant. Do not introduce Neo4j as a new requirement.

SQLite requirements:

- Store UUIDs as TEXT, generated by the application.
- Store timestamps consistently in UTC.
- Store metadata as JSON text, validated by the application and database where supported.
- Enable WAL mode during database initialization.
- Enable foreign keys and configure a busy timeout on every connection.
- Keep write transactions short.
- Use an existing ingestion queue or a dedicated writer where practical.
- Do not perform embedding or network requests inside database write transactions.
- Avoid PostgreSQL-specific SQL, JSONB, and pg_trgm.
- Treat FTS5 as optional and check availability before using it.
- Document the requirement for persistent local storage and the single-writer constraint.

Use migrations compatible with the existing database layer.

## 9. Recognition pipeline

Expose a service equivalent to:

recognize(query, projectId, options) -> RecognitionResult

For each query:

1. Preserve the original query.
2. Identify possible identifiers, phrases, and entity-type hints.
3. Search exact canonical names and qualified names.
4. Search normalized names and aliases.
5. Optionally use bounded fuzzy matching.
6. Search Qdrant for semantic candidates.
7. Merge and deduplicate candidates.
8. Rank using match evidence, query context, and type hints.
9. Detect ambiguity.
10. Optionally expand verified relationships within configured limits.
11. Return a structured result for downstream retrieval.

Do not scan every concept in application memory for every query.

Use type hints as ranking signals rather than strict filters unless the user explicitly requires a type.

Do not directly average incompatible exact, fuzzy, and vector scores. Preserve raw scores and define a documented ranking strategy.

Distinguish:

- accepted matches
- ambiguous candidates
- rejected/low-confidence candidates

Make thresholds configurable and calibratable. Do not describe arbitrary similarity scores as probabilities.

Example result shape:

{
  "query": "Which service handles checkout failures?",
  "recognized_concepts": [
    {
      "id": "...",
      "canonical_name": "PaymentService",
      "type": "service",
      "status": "accepted",
      "match_methods": ["alias", "semantic"],
      "ranking_score": 0.91,
      "source_references": []
    }
  ],
  "ambiguous_candidates": [],
  "relationships": []
}

The numeric value above is illustrative, not a required threshold.

If Qdrant is unavailable, retain exact/alias recognition and return a documented degraded result instead of breaking the entire RAG request.
