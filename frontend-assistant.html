What this topic covers

The Front-End assistant supports Angular, React, and Vue projects alongside their back-end APIs. It uses the indexed source revision for the UI map and uses a versioned Swagger or OpenAPI document for contract checks and code generation.

Start with one immutable revision. Upload or sync the front-end project in Knowledge Base, wait until indexing is ready, and keep the project revision selected while using the assistant.

Step 1: Index the front-end project

  1. Open Knowledge Base → Files and indexing.
  2. Enter a stable project slug for the front-end application.
  3. Upload the source ZIP or connect the repository source when Git source is enabled.
  4. Enter the full lowercase commit SHA for the source revision.
  5. Start parsing and indexing, then wait for the revision to become ready.
  6. Select that revision before opening UI map or contract tools.

Step 2: Add and attach an API contract

  1. Open Knowledge Base → API contracts.
  2. Choose how to load the contract: upload a Swagger/OpenAPI file, use a repository path, or provide a URL.
  3. Create or select the contract version. Keep the version tied to the API revision it describes.
  4. Attach the contract to the front-end consumer project and the back-end provider project.
  5. Reopen the contract entry and confirm both project roles are shown before running checks.

Changing contract records requires the project access role that permits administration of project knowledge. If the contract tab is read-only, ask an administrator to attach the version.

Step 3: Read the UI map

  1. Open UI map from the application tab bar.
  2. Review indexed routes, components, stores, and HTTP requests.
  3. Open a result to inspect its source file and line evidence.
  4. Use the source-based quality checks to find unresolved imports or incomplete static analysis.

The map reflects what the index can resolve. A missing route or component can mean the source was not indexed, the file is outside the uploaded tree, or an import could not be resolved.

Step 4: Check contract conformance

  1. Open the contract’s Checks panel.
  2. Run a consumer check to compare front-end calls and models with the contract.
  3. Run a provider check to compare back-end routes with the contract.
  4. Review each mismatch and open its source evidence before changing code.
  5. Use impact results to see which front-end code is affected by a contract change.

Runtime contract checks compare observed routes and status codes. They do not compare response bodies, so a passing route check does not prove that every response field is correct.

Step 5: Generate client code

  1. Open the contract’s Generation panel.
  2. Select the output you need: TypeScript models, Angular services, React hooks, Vue composables, or mock handlers.
  3. Review the generated files against the selected contract version.
  4. Run the generated code through your project’s normal lint and test workflow before committing it.

When results look incomplete

  • No UI map: confirm the selected revision is ready and refresh the index.
  • No contract checks: add a versioned Swagger/OpenAPI document and attach it to both consumer and provider projects.
  • Many unresolved items: check the indexed source tree and import paths; static analysis depends on what the index can resolve.
  • Status checks pass but behavior is wrong: inspect the application response and add a project-level test because runtime checks do not compare response bodies.
