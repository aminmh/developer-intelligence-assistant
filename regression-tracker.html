What the tracker checks

The tracker compares two ready Git revisions of the same project. It reports changed symbols, impacted routes, API contract changes, package changes, coverage gaps, and verdicts that help you decide where to investigate.

Read the evidence before acting. A result of Suspected regression identifies a difference that needs review. Not covered means the tracker could not verify the behavior with the available code, tests, or runtime evidence.

Step 1: Prepare two revisions

  1. Upload or sync the project’s base revision and wait until it is ready.
  2. Upload or sync the candidate revision and use the same project identity.
    View screenshot
  3. Confirm both revisions have Git commit identifiers and represent the same application.
  4. Open the candidate revision in Code Quality.

Step 2: Start a regression check

  1. Open the Regression check panel.
  2. Choose the base revision in the Base revision selector.
    View screenshot
  3. Click Check for regressions.
    View screenshot
  4. Wait while the app compares changed code and updates the report.
    View reference screenshot
  5. Use the earlier-check selector to reopen a completed comparison.
    View screenshot

Step 3: Read the verdicts

  • Unchanged: the available evidence found no behavior difference.
  • Changed (expected): the behavior changed in a way the evidence treats as consistent with the code change.
  • Suspected regression: the evidence found a difference that needs developer review.
  • Not covered: no sufficient test, route, contract, or runtime evidence was available.

Start with the summary counts, then open the detailed rows. The report includes source paths and line numbers where the analyzer can provide them.

Step 4: Review routes and changed code

  1. Open Routes and sort your attention toward suspected regressions and uncovered routes.
  2. Read the handler path, dependencies, replay result, and any span flags.
    View screenshot
  3. Open Changed code and inspect the reasons attached to each symbol.
    View screenshot
  4. Open API contract changes and check breaking changes before shipping a provider or consumer update.
    View reference screenshot
  5. Review Package changes when a dependency version moved; treat upgrade notes as reference material and confirm them against the package release.
    View reference screenshot

Step 5: Close coverage gaps

  1. Open Not covered by tests or runtime data.
  2. For each item, add or update a project test, verify the route manually, or prepare a replay probe.
  3. Run the comparison again after the evidence is available.
    View screenshot
  4. Use Download characterization tests when the report offers a generated test bundle, then review and adapt those tests in your own project workflow.

Optional replay

Replay is an additional comparison for configured HTTP targets. The developer runs both application versions; the assistant only sends HTTP requests and displays the differences.

  1. Configure a base target and a candidate target that you can safely call.
  2. Use read-only routes by default. Write requests are permitted only when the target is explicitly marked disposable.
    View screenshot
  3. Run or import probes, then review response differences per route.
    View screenshot
  4. Check p95 and exception/span flags when runtime evidence is attached to the replay.
    View reference screenshot
  5. Do not treat replay as a build or test runner: the app does not start your project, execute project code, or run your project’s test suite.
    View screenshot

How to interpret the result

  • Investigate every suspected regression before release.
  • Document why an expected change is safe when the report shows changed behavior.
  • Prioritize uncovered routes and symbols when the change is high risk.
  • Keep replay recordings in the app’s storage boundary; they are not runtime telemetry.
